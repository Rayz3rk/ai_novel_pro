# 创作方法评测与匿名质量对照

## 1.1 的评测入口

创作记录中的“导出冻结评测样本”保存本次材料、原始输出、技能/提示快照、公开模型参数和调用记录。样本从应用接口导出，因此不依赖当前使用 SQLite 还是 PostgreSQL。连接密钥不会导出；文件仍包含作品材料，应按作品备份保管。

1.1 的整理工具全部离线运行，不读取个人数据库，不访问凭据，不补发模型调用。旧的 `tests/quality/generate-baseline.ts` 已变为同一离线工具的兼容入口，不再直接打开 SQLite 或连接平台。

## 先验证确定性机制

在源码根目录使用 Node.js 24 与 pnpm 11：

```powershell
pnpm eval:creative
```

默认报告写入 `test-results/creative-evaluation/report.json`。案例覆盖技能适用范围、受限导入、声音/偏好/秘密隔离、可选资源、预览无任务写入，以及基础稿件清洁。运行使用独立临时数据、内存 SQLite，并阻止网络请求；报告的 `modelRequests` 应为 0。

这组案例不评价文笔、情节吸引力或 Skill 的文学收益。每个新增方法仍应有自己的功能案例，文风效果另外比较。

## 单份样本的离线检查

先从书间创作记录导出 JSON，然后运行：

```powershell
pnpm compare:creative --sample samples/candidate.json --out test-results/creative-review/single-01
```

所有相对路径以源码根目录解析，即使通过 pnpm 子工作区执行也是如此。输出目录必须是新目录，已有结果不覆盖。

`evaluation.json` 记录提示摘要、技能版本、调用次数与提示摘要、字符数和清洁提示，不自动计算文学质量总分。旧任务缺少完整提示或参数时，可以单独分析已有内容，但不能冒充完整冻结的同条件实验。

## 两份已完成样本的 Skill 比较

如果作者选择实际比较，可在同一保存稿和相同模型参数下，分别使用某个方法和基础任务，明确发起两个正常任务。这些调用继续使用应用自己的预算、记录和采纳机制。离线工具不会替作者生成第二份输出，也不会为了凑样本重新发送任务。

导出两份已完成输出后：

```powershell
pnpm compare:creative --sample samples/with-method.json --baseline samples/base.json --out test-results/creative-review/pair-01
```

比较前会检查：

- 来源是两个独立、已完成且有非空输出的任务。
- 任务类型、正文输入版本、模型及公开生成参数相同。
- 非技能材料相同，系统任务规则相同；只有 Skill 及其对应材料可变化。
- 材料与初次实际提示一致，首个调用与初次快照一致。
- 提示和各次调用哈希正确，调用归属正确，最终输出与最后成功调用一致。

缺少快照、材料有变化或模型参数不同的样本会被拒绝标记为同条件对照。若某个 Skill 占用预算导致其他材料被裁掉，也不满足此处的严格比较条件，应先缩小样本、固定材料后重新设计实验。

哈希用于核对记录是否一致，不是供应商签名；这些检查不能独立证明模型实际执行，更不能证明哪份文笔更好。遇到修正/重试，应一起查看每次调用和费用，不能只看最终稿。

## 匿名评阅

双样本成功后生成 `comparison.json`，可用 Python 3 的标准库创建本机匿名页：

```powershell
python tests/quality/prepare_review.py test-results/creative-review/pair-01/comparison.json test-results/creative-review/pair-01/blind
```

打开生成的 `review.html`，先按可读性、情节推进、人物表现、与要求一致、省改稿程度评价 A/B，再导出匿名评分。评分之后再查看 `identity-after-review.json`。

同一来源重复准备会复用原身份对应，不重新随机排序；不同来源不能覆盖已有评阅目录。页面不上传评分。单对样本不能代表所有题材、整部小说或整个产品，自动化测试填写的评分也不算作者评价。

样本、评分和身份文件是独立实验材料，应单独保留；它们不是作品正文或事实确认的一部分。固定样本只验证工具功能，不作为文学质量结论。
